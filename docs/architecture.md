# Архитектура приложения

```text
PySide6 GUI + отдельное окно логов
  │ команды / события JSON / отмена (QProcess)
  ▼
Worker — одна задача, один процесс
  ├── каталог: веса + конфигурация + лицензия + SHA-256
  ├── decode / streaming overlap / export (WAV, MP3)
  └── create_engine → StemEngine
        └── backends/audio_separator.py
              ├── RoFormer для вокала
              └── Demucs для мелодий
```

**Интерфейс адаптера:** `separate(audio) -> audio`, `audit() -> dict`.
Форма: `(frames, 2)`, float32, 44100 Hz; результат той же длины, без нормализации
отдельных окон. Только CPU. Ошибки передаются исключениями. Во время инференса
адаптер не скачивает веса. Интерфейс не зависит от PyTorch, ONNX или Qt.

**Владение:** worker декодирует вход, загружает одну модель, обрабатывает поток
окон с перекрытием, сохраняет временный float32-стем, освобождает модель и только
затем загружает следующую. GUI не владеет моделями и не импортирует PyTorch.
Временные файлы принадлежат конкретной задаче; готовый отчёт появляется после
успешного экспорта. Исходник не перезаписывается.

`worker.py` отвечает за CLI, проверку входа, статус задачи и итоговый отчёт.
`pipeline.py` импортируется только после проверки входа: выполняет декодирование,
последовательные стадии моделей и экспорт. Каждая стадия возвращает типизированные
метрики без ссылки на модель; сборка мусора происходит до создания следующей модели.
В `audio.py` отдельно находятся проверка формата/пиков и WAV/MP3-экспорт, а связанные
настройки streaming-окна собраны в неизменяемый `StreamWindow`.

GUI собирается небольшими методами для шапки, входа, настроек, диапазона и действий.
Тесты взаимодействуют через кнопки, Qt-сигналы и интерфейс запуска/событий задачи,
а не вызывают приватные обработчики виджетов напрямую.

**Одна активная задача:** очереди и истории задач в GUI нет. Разделение и скачивание
моделей используют один слот `active`; повторный запуск игнорируется и на уровне
обработчиков, и на уровне запуска worker. Пока задача активна, кнопка запуска,
скачивание и редактирование входа/настроек недоступны. После выхода worker слот
освобождается, текущий файл убирается из окна; следующая задача запускается только
пользователем. Закрытие окна отменяет единственную текущую задачу.

**Прогресс:** скачивание — реальные байты; разделение — завершённые аудиоокна.
Для двух стадий каждая занимает половину шкалы независимо от скорости модели.
Это доля работы по окнам, **не** оценка оставшегося времени. В пределах одного
внешнего окна есть пауза между обновлениями; журнал движка показывает внутренние
итерации. Декодирование, загрузка и экспорт — индикатор ожидания, завершение — 100%.
При каждом новом запуске прогресс сбрасывается; после отмены/ошибки — 0%.
События прогресса после запроса отмены не обновляют статус и шкалу.

**Волна и диапазон:** `waveform.py` отдельно от inference-адаптеров. FFprobe сообщает
длительность, FFmpeg потоково вычисляет пиковые уровни блоков. В GUI попадает
1200 пиков, не декодированный трек. Процессы работают асинхронно; смена файла
отменяет старый анализ и инвалидирует его события. Два маркера и числовые поля
синхронизированы. По умолчанию — 0:00 → EOF; CLI получает `--full` либо
`--start`/`--duration`, зафиксированные при нажатии «Запустить».

**Жизненный цикл процессов:** `guardian.py` запускается отдельно от тяжёлого runtime.
Он проверяет идентичность GUI/worker (PID + creation time) и завершает только
принадлежащую задаче семью процессов при аварийном исчезновении родителя/worker.
POSIX-worker получает собственную сессию/process group; Windows-worker — Job Object.
`tool_runner.py` применяет такое же владение к FFprobe/FFmpeg превью, даже когда
пользователь ещё не запустил инференс. Поэтому закрытие GUI во время построения
волны не оставляет неприкреплённый долгоживущий аудиопроцесс.

GUI дополнительно отслеживает отсутствие прогресса и исчезновение файлов, выполняет
terminate → kill **только самого worker** при отмене/закрытии. GUI не обходит дерево
и не завершает guardian: очисткой семьи процессов владеет только `guardian.py`.
`start_parent_guard` вызывается один раз перед работой; надзор действует до фактического
выхода worker, включая нормальный выход, отмену и исключения. После очистки guardian
завершается сам; при принудительной остановке очистка может закончиться уже после
закрытия GUI. Обычные FFmpeg-вызовы по-прежнему ожидаются своим непосредственным
родителем, а не guardian. Внешние FFmpeg-вызовы worker ограничены
`subprocess.run(timeout=...)`. Это не гарантия выполнения finally при SIGKILL/потере
питания: временные файлы не должны интерпретироваться как готовые результаты.
Встроенный плеер удалён по запросу пользователя; GUI не держит аудиофайлы открытыми
после экспорта. Прослушивание — во внешнем плеере через папку результата.

**Расширение:** новую совместимую модель добавляют в каталог; новую архитектуру
или фреймворк — отдельным адаптером с подключением в `create_engine`. Тесты worker
подменяют эту же фабрику и проверяют, что модели не живут одновременно. GUI и
аудиообработка не должны меняться при смене фреймворка.

**Чего намеренно нет:** системы динамических плагинов, универсального графа
моделей, event bus, загрузки произвольного Python-кода, нескольких параллельных
моделей и отдельного виртуального окружения для каждого из них.
Когда появится второй реальный backend с несовместимыми зависимостями, его можно
вынести в собственный runtime-процесс с тем же протоколом команд/событий.
Подготовка переносимых runtime и бинарных сборок остаётся отдельной работой.
